## 两个一跑就报错的硬错误

### 1. 表 4 写了两个 `material_id`（同一个列名写了两遍）

你的原文：「系统出题/资料id(外键)，资料id(外键)，id（主键），答题时间」—— 两个「资料id」。

实测：

```
OperationalError: duplicate column name: material_id
```

**表建不出来。** 第二个大概是笔误（本来想写别的东西）。

### 2. 条目表的外键指向了计划的「日期」列

`新日期(外键 ondeletecascade)` —— 你想让条目挂在计划的日期上。实测：

```
插入时 OperationalError: foreign key mismatch - "plan_items" referencing "day_plans"
```

原因（课 0004 讲过）：**外键的目标必须是主键或 UNIQUE 列**。`plan_date` 两者都不是。
所以条目该指向计划表的 **`id`**（也就是 `plan_id`），不是日期。

## 一个回归，以及它的连锁后果

**表 3 的 `user_id` 外键被删掉了。**（v3 里有「人id(外键 on delete cascade)」）

实测连锁反应：

```
删用户前: users=1 plans=1 materials=1 questions=1 answers=1
删用户后: users=0 plans=0 materials=1 questions=1 answers=1
```

计划跟着没了，但**资料、题目、答题记录全成了孤儿** —— 链条在 `materials` 这里断了（它不再指向用户）。

这是「多用户隔离」那条硬约束的命门：**资料不知道属于谁了**，也就谈不上按用户隔离。

## 还没改的

- 题干依然不在题目表里（只留了 `id`）—— 上轮指出过，题目表存在的理由就是存题干
- 「答题时间」依然在题目表里（属于「一次作答」）
- 标准答案依然在答题记录里（跟「题目」是一对一）—— 第三轮了
- 「日历」「新日期」「计划」三个字段名分不清谁是谁
- 表 3 的 UNIQUE 还是没说到具体哪几列；`(user_id, name)` 这组仍未落地

## 结论：换媒介

三轮下来每轮都是「改对 1–2 处、新引入 1–2 处」。**问题不在你，在媒介** —— 中文散文表达不了「哪一列是主键、外键指向哪一列」这种结构信息，写着写着就串了。

## 写 SQL 之前必须先定的三件事（脚本查不出来）

这三条是**语义**问题，`run_schema.py` 只会查语法和结构，查不出「字段放错表」。所以得你自己定：

1. **题目表里没有题干** —— 现在只有 `id`。题目表存在的理由就是存题干和标准答案
2. **「答题时间」在题目表** —— 它属于「一次作答」，不属于题目（答 3 次只会剩最后一次的时间）
3. **标准答案在答题记录里** —— 它跟「题目」是一对一，跟「一次作答」不是（答 10 次存 10 遍）—— 这是第四轮了

## 落成 SQL 时注意

- **列名一律用英文**：`user_id` / `plan_id` / `question_id` / `material_id`。
  中文列名 SQLite 允许，但进了 SQLAlchemy / Pydantic 会很难用（sql库 的约定：字段名用英文，中文只出现在数据值里）
- 表 4 那行有个多余的逗号（`）`前有两个「，」）
- 表 3 的外键补上 `ON DELETE CASCADE`
- 每张表都要能写出 `FOREIGN KEY (plan_id) REFERENCES day_plans(id)` 这样的整句
- 表 5、表 6 两行空标题可以删掉了
