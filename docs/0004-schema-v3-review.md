## 一条原则，解决其中四个问题

**外键指向「直接的父」，不是家族的祖先。**

问法：**这一行数据最直接的「父亲」是谁？**

两条链子：
- `用户 → 计划 → 条目`
- `资料 → 题目 → 作答`

每一层只认自己的**直接上一级**。你把好几处都一路指到了「用户」，于是中间那层关系丢了。

### 证据 A：条目表只挂用户 → 关系丢了

表里有两条计划（10-15、10-16）和两条条目。实测：

```
('20:00', '复习 B+ 树', 1)
('21:00', '背单词', 1)
```

**想查「2026-10-15 这天计划里的条目」—— 写不出来。** 条目只连着用户，跟哪条计划毫无关系。

用户再加 3 条计划、10 条条目之后，全糊在一起。

### 证据 B：标准答案放在答题记录 → 同一句话存 N 遍

同一道题答 3 次，实测：答题记录 **3 行**，不同的标准答案 **1 份** —— 但那一句标准答案存了 **3 遍**。

**判据**：标准答案跟「题目」是一对一（一道题一个），跟「一次作答」不是。答 10 次就 10 份。

### 证据 D：「答题时间」放在题目表 → 历史被覆盖

同一道题答了三次，题目行只有一行，实测 `answered_at = 2026-10-22 21:00` —— **只剩最后一次**。
想统计「哪天答过 / 连续打卡几天」全丢了。

「答题时间」绑定的是**一次作答**，不是题目。

### 好消息：指对之后，「怎么级联删」自动解决

外键指向直接父亲，删用户时链式 `ON DELETE CASCADE` 会一路传下去（`users → 计划 → 条目`、`资料 → 题目 → 作答`）。
不用你为「连带删除」单独设计任何东西。

## 表 3 的 UNIQUE 加错位置

你写「资料id(主键)唯一」→ **等于没加**：`id` 本来就是主键，本来就唯一。

实测代价：同一个用户传了两份同名 `notes.pdf`，两份都进去了。

真要管的是：**同一个人不能有两份同名资料** → 约束加在 `(user_id, name)` 这一组上。
判断方法：**把「不能重复」这句话里的主语找出来** —— 主语是「谁 + 什么」，约束就加在那几列上。

## 表 4 的题干没了

你把「题目」这一列删掉了，只留了「题目id」。结果：**题目表里没有题目内容。**

题干是这张表存在的理由 —— 没有它，出题、判分全都无从谈起。

## 命名老账（第三次了，这次一定改掉）

- **主键字段名统一叫 `id`**
- **外键列名 = `引用表名单数_id`**：`user_id`、`plan_id`、`question_id`、`material_id`
- 「个人日历（主键）」「plan(主键)」「id（外键）」这类写法**在 SQL 里根本写不出来** —— 这不是措辞问题，是还没想清哪一列是主键、哪一列是外键

自检法：**每张表你都得能写出这句话** —— `FOREIGN KEY (plan_id) REFERENCES day_plans(id)`。写不出，就是还没定下来。
