## 表 1 · 用户信息

**对的**：这是根表，`id` 做主键、没有外键 —— 结构正确。

**改：`nickname` 不该 UNIQUE（约束过头）**

你写「id email nickname 只能出现一次」。实测第三个人想叫「阿宝」（邮箱不同）：

```
IntegrityError: UNIQUE constraint failed: users.nickname
```

问自己一句：**昵称是「身份」还是「称呼」？** 两个人同名同姓都很正常，撞个昵称凭什么不让？

（`id` 那条是多写的：主键本来就唯一，不用再声明一次 UNIQUE。）

**改：`code` 是什么？**

如果它是密码，两件事：

1. 名字直接叫 `password` —— 三个月后你自己看得懂
2. **绝对不能存明文**。要存哈希值（bcrypt / argon2），登录时把用户输入算成哈希再比对。这是第 3 周「注册登录 + JWT + 哈希」的核心，也是面试必问

实测：`code` 列没加 `NOT NULL`，我插了一条 `code = NULL` 的用户 —— 成功了。空密码的账号能建出来。

**缺（可选但建议）**：`created_at` 注册时间。几乎每张表都会想要它。

## 表 2 · 计划 —— 这条最要命

**问题：把「计划」和「计划条目」压成了一行。**

动作 2 的原话是「给某一天建**一条**计划，计划里能写**好几个**条目」= 一对多。

实测：今天要写两条（20:00 复习 B+ 树、21:00 背单词），只能在表里放成两行。然后查「我 2026-10-15 的计划」：

```
拿到 2 行：
  ('2026-10-15', '20:00', '复习 B+ 树')
  ('2026-10-15', '21:00', '背单词')
```

问自己：**这到底是「一条计划里的两个条目」，还是「两条各自独立的计划」？** 你现在的表区分不出来。

而且「天」这一层没有任何字段（没有标题、没有「今天完成没有」）—— 因为它根本没有独立的一行。

**改：`id(外键)` 两个毛病**

- **角色混了**：一列不能同时是主键又是外键 —— 除非你要的就是「一个用户一辈子只有一条计划」。你确定吗？
- **命名**：指向 `users` 的外键该叫 `user_id`（参考卡 04 第 8 节）

**改：三个时间字段互相打架**

`日期date`、`clock时刻`、`date_plan` 三个都在描述时间。一行只能有一个 `clock`，那第三个条目要放哪？**你写了三个时间字段这件事本身，就说明该拆表。**

**问自己**：动作 2 说「某一天建**一条**计划」—— 同一个人、同一天建第二条，该不该允许？（想想 `UNIQUE (user_id, plan_date)`）

## 表 3 · 资料

**对的**：资料表有主键 + 指向用户的 `user_id` 外键 —— 方向对（比表 2 好）。

**改：`belong 是否属于` 是冗余列**

`user_id` 已经在表达「属于谁」。实测：

```
INSERT INTO materials (user_id, belong, name) VALUES (NULL, 1, '矛盾.pdf')
-> 成功
```

`belong = 1`（属于）和 `user_id = NULL`（不属于任何人）**各说各话，数据库不拦**。冗余列的代价就是这个：同一件事实有两个来源，迟早不一致。

（猜你的原意：是不是想说「这份资料是公开还是私有」？那是另一件事，该叫 `is_public` 或 `visibility`。）

**改：缺「文件还是网址」**

动作 3 是「一份文件**或**一个网址」。现在只有一个 `name`，分不出它是啥。需要一个类型字段 + 存放位置（`path` 或 `url`）。

再往远看一步：第 7 周要做「切分 + 向量库」，资料的**正文**得先有地方存（或至少存路径）。

**改：硬约束没落实**

「**不同用户的同名资料不能互相盖掉**」—— 你的唯一约束该加在哪几列上？

实测两个方向：

```
两个用户各传一次 notes.pdf   -> 都进去了  ← 这是对的
同一个用户传两次 notes.pdf   -> 也进去了  ← 这是错的
```

想想：**约束该加在 `name` 一列上，还是加在几列的组合上？**

**缺（可选）**：`created_at` 上传时间。

## 表 4 · 系统出题 —— 两张表挤成一张

**问题一：把「题目」和「答题记录」混在一张表**

题目生成一次就固定；答题记录可以有很多条（今天答错、一周后复习再答一次）。

实测：同一道题答两次：

```
题目表行数 = 2，不同的题目 = 1
```

答 10 次就存 10 份题干 + 10 份标准答案。想统计「**这道题我错过几次**」还得按题干文字去分组。

问自己：**「一道题」和「一次作答」是同一条数据吗？**

**问题二：没有主键**

自检第 1 问你答不上来 —— 这行数据的身份证是什么？

**问题三：`个人id(外键)` 是冗余的**

题目属于资料，资料属于人 → 用户归属**能间接算出来**（多 join 一次）。冗余存不是绝对禁止（有时为了查询方便会存），但你要知道代价：多一个可能不一致的事实来源。

**问题四：`出题动作` 这一列不该存在**

它存的是**动作**，不是数据。（和表 5 是同一个毛病的轻症版。）

**问题五：`判的答案` 分不清**

三个字段摆在一起：`std_answer`（标准答案）、`user_answer`（我答的）、`判的答案`（？）。第三个如果意思是「对还是错」，那就叫 `is_correct`。

**顺手**：`answered_at`（答题时间）在没答过时是空的 —— 拆表之后这个问题自动消失。

## 表 5 · 数据删除 —— 它不是表

**「删用户时连带删他的数据」不需要新建一张表。** 它是**外键上的 `ON DELETE CASCADE`**。

课 0004 第 4 节实测过：

```sql
DELETE FROM users WHERE id = 1;
-> users = 0 ，plans = 0     -- 用户和他的计划一起没了
```

**判断法（记住这一句）**：**表存的是「状态」（名词），不是「动作」（动词）。** 问自己「这一行数据是什么？」—— 答不上来，它就不是表。

不过你的**意识是对的**：你知道要级联删。只是找错了地方 —— 把它挪到表 2、表 3、表 4 那些外键的定义上去。
